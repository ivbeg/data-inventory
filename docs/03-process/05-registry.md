# Реестр данных

Реестр данных — главный результат инвентаризации: по строке на каждый набор, с владельцем, доступом и датой. Минимальный состав записи — 14 атрибутов; их достаточно, чтобы набор можно было найти, понять, кому писать и можно ли его получить. Расширенный состав связывает набор со схемой, системой, полномочием и нормативным актом. Если сведение найти не удалось, пишут «не установлено» и где искать дальше: честный пропуск полезнее догадки.

## Минимальный состав

| № | Атрибут | Что писать |
|--:|---------|------------|
| 1 | **Уникальный идентификатор** | Короткий код или номер, который не меняется |
| 2 | **Наименование** | Официальное название набора или ресурса |
| 3 | **Описание** | Что описывает набор, за какой период и территорию |
| 4 | **Ответственный** | ФИО сотрудника ИТ-подразделения, который отвечает за данные, — не пресс-службы |
| 5 | **Контакты ответственного** | Почта, телефон |
| 6 | **Периодичность обновления** | Ежедневно, ежемесячно, ежегодно, не обновляется |
| 7 | **Режим доступа** | Открытый, ограниченный, закрытый — с основанием ([«Доступ и ограничения»](./06-access.md)) |
| 8 | **Ссылка для выгрузки** | Адрес файла или программного интерфейса, если набор опубликован |
| 9 | **Формат распространения** | CSV, JSON, XML, XLSX, API |
| 10 | **Дата публикации** | Когда набор впервые стал доступен |
| 11 | **Дата последнего изменения** | Когда обновлены данные |
| 12 | **Отметка о контроле качества** | Проверено ли качество, когда и с каким результатом ([«Качество данных»](./07-quality.md)) |
| 13 | **Условия использования** | Лицензия или условия соглашения |
| 14 | **Организация-владелец** | Владелец или оператор набора |

## Расширенный состав

- **Схема и структура данных** — поля, типы, справочники.
- **Информационная система** — в какой системе ведётся набор.
- **Полномочие** — функция владельца, ради которой собираются данные ([«Владельцы и полномочия»](./03-owners-and-mandates.md)).
- **Нормативный акт** — закон, постановление, приказ.
- **История изменений** — версии набора.
- **Уровень обслуживания** — обязательства по доступности и качеству.
- **Дата проверки записи** и **откуда известно о наборе** — для того, кто будет реестр обновлять.

Минимальный и расширенный состав предложены в презентации автора и повторены в обзоре по Казахстану 2025–2026 годов. Чтобы реестр можно было обменивать с каталогами, атрибуты стоит сопоставить со стандартом описания — DCAT или его европейским профилем DCAT-AP ([«Стандарты описания»](../05-frameworks/02-metadata-standards.md)).

## Пример записи

| Атрибут | Значение |
|---------|----------|
| Идентификатор | `regional-hospitals` |
| Наименование | Сведения о медицинских организациях по регионам |
| Описание | Перечень медицинских организаций с адресом, типом и числом коек, по регионам |
| Ответственный | не установлено — искать в положении о ведомственной системе |
| Периодичность обновления | ежеквартально (по описанию системы) |
| Режим доступа | ограниченный — выдаётся по межведомственному запросу |
| Ссылка для выгрузки | нет |
| Организация-владелец | Министерство здравоохранения |
| Информационная система | Ведомственная система здравоохранения |
| Дата проверки | октябрь 2026 года |

Пример условный: он показывает, как выглядит запись, когда часть сведений не найдена.

## Один набор под разными именами

Один и тот же набор встречается под разными именами: полное название, сокращение, адрес сайта. Если записать его трижды, реестр покажет три набора там, где есть один. Чтобы этого не случилось:

- **идентификатор** — и связи с задачами и вопросами через него, а не через название;
- **синонимы** — в отдельной колонке;
- **поиск перед добавлением** — по синонимам и адресу;
- **общий список** для источников, которые повторяются от задачи к задаче.

## Одинаковая подробность

В одном реестре записи должны быть одинаково подробными. Если перечислить источники поштучно невозможно («сайты нефтяных компаний»), записывают **группу** с пометкой и поясняют, что в неё входит и почему она не раскрыта.
